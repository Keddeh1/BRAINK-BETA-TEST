# BRAINK architecture development and automation

Ten executable operations extend the separate BRAINK application node. The operator surface is keddeh.com/braink/architecture. Existing native owner identity and worker bearer contracts apply; no added approval system is introduced.

| Target | Execution and evidence |
|---|---|
| Reconciliation | Catalogue occurrences compared with deployed ceremonies and independently read local VFS definitions. |
| Evolution | Function hashes and family/variant/colony dependencies determine affected clean-build sectors. |
| Continuity | Existing owner VFS subscription registration, verified content mirroring and monotone cursor readback. |
| Feedback | Actual owner observer_calibrate implementation; RELATIONAL_ANCHOR exchange, deduplication and recipient inbox readback. Calibration metadata does not establish empirical learning. |
| Ceremonies | Native instance ceremonies resume, retain per-instance VFS, and verify hub and mesh subscriptions. |
| Delivery | Four separate clean sector qualifications; downloaded wheel hash and source-family identity verification; immutable source activation and supervised restart. |
| Diagnostics | Actual service responses, process observation and outbox state; restart remains under the existing node supervisor. Unisolated root causes retain their uncertainty. |
| Placement | Measured CPU, memory, disk and load; source-compatible host placement protocol. Cross-host execution is recorded only when observed. |
| Recovery | SQLite backup, immutable-object checkpoint, clean reconstruction, receipt-chain verification and restored mesh network readback. Physical host loss/reboot are separate unexercised properties. |
| Development | Evidence-derived repair and qualification work, executable function routes and retained task frontier. Novel source generation requires an actual owner development route. |

Every target execution uses its catalogue function module, core family variant and colony occurrence, with its own instance VFS, subscription and ceremony. Aggregate evidence also has actor/observer receipts. A durable website outbox sends verified artifact bytes to the existing website D1/R2 stores; replay preserves the newest observation.

`braink-node automate run --config <private-config>` executes all ten; `status`, `serve`, and `host-server` expose observation, unattended cycles and actual host placement. Configuration contains existing credential file references, active immutable source, desired branch checkout and explicit scheduling cadences. Secrets remain outside Git.

Updates remain on feat/braink-application-node. Other sectors remain in the deployment manifest when a single sector changes. Qualified updates restart only this application's supervised processes. Reconstruction writes a fresh destination and does not replace other nodes.

External assessment report references remain unset until another system returns an actual report document number. Build tests and runtime readback are engineering evidence, not an external assessment.
